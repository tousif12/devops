# Ubuntu Commands for Your DevOps Journey

A practical reference with **455 copyable command examples**, simple use cases, troubleshooting steps, and beginner labs.

This covers the commands you are likely to need from Linux fundamentals to cloud automation. No finite guide contains every Linux command or option. Learn the task first, then look up the command when needed.

## How to use this guide

- **Run Ubuntu commands inside Ubuntu**, either in the VM console or after SSH. Windows/Git Bash host commands are explicitly marked in the Vagrant section.
- Copy **one code block at a time**. Blocks appear with copy controls in Markdown viewers that support them; the `.md` file itself cannot add a universal copy button.
- Replace example usernames, IPs, paths, repository URLs, resource names, and PIDs with your actual values. Example files such as `app.log`, `deployment.yaml`, and `worker.sh` must exist first.
- `sudo` means run with administrator privileges. A password prompt usually shows no characters as you type.
- Commands marked **DELETES**, **OVERWRITES**, **CHANGES**, **STOPS**, or similar alter data or running systems. Practice on your VM first; they are examples, not an installation script.
- Most examples fit modern Ubuntu Server installations using Bash and systemd. Optional tools, package availability, service configuration, and permissions vary. Check `command --help` and `man command` on your machine.
- Docker, Git, Kubernetes, Helm, Terraform, Ansible, AWS CLI, and Vagrant are separate DevOps tools. Their sections are included because they are part of the journey.

### Terminal shortcuts

| Shortcut | Use case |
| --- | --- |
| Tab | Complete a command or path; double Tab can show candidates |
| Up / Down | Revisit previous commands |
| Ctrl+C | Interrupt the foreground command |
| Ctrl+D | Send end-of-input; at an empty shell prompt, exit |
| Ctrl+L | Clear the display |
| Ctrl+R | Search shell history; avoid secrets in command history |
| Ctrl+A / Ctrl+E | Move to start/end of the current command |
| Ctrl+U / Ctrl+K | Delete text before/after the cursor |
| Ctrl+Z | Suspend a job; use `jobs`, `fg`, or `bg` afterwards |
| q | Exit `less`, `man`, and many pagers |
| tmux: Ctrl+B, then D | Detach while the session keeps running |

### Path and symbol basics

| Symbol or path | Meaning |
| --- | --- |
| `/` | Filesystem root |
| `~` | Current user's home |
| `.` / `..` | Current directory / parent directory |
| `/home/devops` | Example regular-user home |
| `/etc` | System configuration |
| `/var/log` | Common log-file location |
| `/opt` | Common location for additional applications |
| `/tmp` | Temporary files; do not rely on permanent retention |
| `/dev` / `/proc` / `/sys` | Devices and kernel/system interfaces |
| `*` | Shell wildcard; use quotes when you want a literal pattern |
| `|` | Send stdout into another command |
| `>` / `>>` | Overwrite / append stdout to a file |
| `&&` / `||` | Run next command on success / failure |
| `&` | Start a job in the background |
| `#` | Start a shell comment when unquoted and in comment position |

## 05. Search files and text

grep searches content. find searches names and file properties. Quote patterns so the shell does not expand them first.

### 05.01 — Search for a word in a log

```bash
grep 'ERROR' app.log
```

### 05.02 — Ignore capitalization and include line numbers

```bash
grep -in 'error' app.log
```

### 05.03 — Search all text files under a project

```bash
grep -RIn 'DATABASE_URL' ./project
```

### 05.04 — Show lines that do not contain a word

```bash
grep -v 'DEBUG' app.log
```

### 05.05 — Show context around a match

```bash
grep -n -C 3 'ERROR' app.log
```

### 05.06 — Match several words

```bash
grep -En 'ERROR|WARN' app.log
```

### 05.07 — Match an exact text string without regex interpretation

```bash
grep -Fn '192.168.1.201' app.log
```

### 05.08 — Find Python files under your practice directory

```bash
find ~/devops-lab -type f -name '*.py'
```

### 05.09 — Find directories named logs

```bash
find ~/devops-lab -type d -name logs
```

### 05.10 — Find files modified within the last day

```bash
find ~/devops-lab -type f -mtime -1
```

### 05.11 — Find files larger than 100 MiB

```bash
find ~/devops-lab -type f -size +100M
```

### 05.12 — Find files owned by the current user

```bash
find ~/devops-lab -type f -user "$USER"
```

### 05.13 — Print filenames safely when names may contain spaces or newlines

```bash
find ~/devops-lab -type f -print0
```

### 05.14 — Search quickly with ripgrep; requires ripgrep

```bash
rg -n 'ERROR|WARN' ./project
```

### 05.15 — List project files with ripgrep

```bash
rg --files ./project
```

### 05.16 — Preview old logs before deciding whether to remove them; this command does not delete

```bash
find ~/devops-lab -type f -name '*.log' -mtime +7 -print
```

## 06. Pipes, redirection, and text processing

A pipe | sends output to the next command. > overwrites; >> appends. Standard output is stream 1, standard error is stream 2.

### 06.01 — OVERWRITES: write text to a file

```bash
printf 'Hello DevOps\n' > notes.txt
```

### 06.02 — Append a line

```bash
printf 'Ubuntu practice\n' >> notes.txt
```

### 06.03 — Redirect errors to a separate file

```bash
ls /missing-directory 2> errors.txt
```

### 06.04 — Capture stdout and stderr in one file; the order matters

```bash
bash script.sh > run.log 2>&1
```

### 06.05 — Display output and save it at the same time

```bash
printf 'deployment started\n' | tee deploy.log
```

### 06.06 — Append to a protected file using tee

```bash
printf 'lab entry\n' | sudo tee -a /var/tmp/devops-demo.txt
```

### 06.07 — Count matching log lines

```bash
grep -c 'ERROR' app.log
```

### 06.08 — Sort lines alphabetically

```bash
sort names.txt
```

### 06.09 — Sort numbers numerically

```bash
sort -n numbers.txt
```

### 06.10 — Remove duplicate lines; sort first because uniq handles adjacent duplicates

```bash
sort names.txt | uniq
```

### 06.11 — Count repeated lines

```bash
sort names.txt | uniq -c | sort -nr
```

### 06.12 — Print the first whitespace-separated field

```bash
awk '{print $1}' access.log
```

### 06.13 — Print usernames from the colon-separated account file

```bash
cut -d: -f1 /etc/passwd
```

### 06.14 — Preview a replacement without editing the file

```bash
sed 's/dev/staging/g' config.txt
```

### 06.15 — OVERWRITES CONTENT: replace text and retain a .bak backup

```bash
sed -i.bak 's/dev/staging/g' config.txt
```

### 06.16 — Print lines 10 to 20

```bash
sed -n '10,20p' app.log
```

### 06.17 — Convert lowercase to uppercase

```bash
printf 'devops\n' | tr '[:lower:]' '[:upper:]'
```

### 06.18 — Pretty-print JSON; requires jq

```bash
jq . response.json
```

### 06.19 — Extract a JSON field

```bash
jq -r '.status' response.json
```

### 06.20 — Safely pass a list of file paths to another command

```bash
find ~/devops-lab -type f -print0 | xargs -0 -r wc -l
```

## 09. Permissions and ownership

r=read (4), w=write (2), x=execute or directory traversal (1). Order: owner, group, others. A directory needs x to access its contents. Avoid chmod 777.

### 09.01 — Inspect permissions and ownership

```bash
ls -l script.sh
```

### 09.02 — Make a script executable for its owner

```bash
chmod u+x script.sh
```

### 09.03 — Give owner full access and everyone else read/execute

```bash
chmod 755 script.sh
```

### 09.04 — Allow owner read/write and group/others read

```bash
chmod 644 config.txt
```

### 09.05 — Restrict a private key to its owner

```bash
chmod 600 ~/.ssh/id_ed25519
```

### 09.06 — Restrict SSH directory access to its owner

```bash
chmod 700 ~/.ssh
```

### 09.07 — Change ownership of one file

```bash
sudo chown devops:appteam config.txt
```

### 09.08 — RECURSIVE CHANGE: change ownership only within the named application directory

```bash
sudo chown -R devops:appteam /opt/myapp
```

### 09.09 — Change a file's group

```bash
sudo chgrp appteam config.txt
```

### 09.10 — Show default permission masking for new files

```bash
umask
```

### 09.11 — Set a more private mask for this shell's new files

```bash
umask 027
```

### 09.12 — Inspect permissions of every path component when access is denied

```bash
namei -l /opt/myapp/config.txt
```

### 12.02 — List running services


### 12.03 — List service installation and enablement states


### 12.04 — Start an installed web server

### 12.05 — STOPS WEB SERVICE: stop Nginx


### 12.06 — INTERRUPTS SERVICE: restart Nginx

```bash
sudo systemctl restart nginx
```

### 12.07 — Reload Nginx configuration after validating it


### 12.08 — Enable Nginx at boot


### 12.09 — Disable Nginx at boot; does not stop it now


### 12.11 — Check whether a service is active


### 12.13 — View a service's unit file and overrides

### 12.14 — Reload systemd unit definitions after editing unit files; does not restart the app

## 36. Practice lab: a health-check Bash script and cron

**Goal:** check the local lab website and log a timestamped result. Start the section 35 service while practicing this section.

### Step 1 — Create a script directory

```bash
mkdir -p ~/scripts
nano ~/scripts/healthcheck.sh
```

Paste:

```bash
#!/usr/bin/env bash
set -u

url='http://127.0.0.1:8000/'

if /usr/bin/curl --fail --silent --show-error --max-time 5 "$url" > /dev/null; then
    printf '%s OK %s\n' "$(date -Is)" "$url"
else
    printf '%s FAIL %s\n' "$(date -Is)" "$url" >&2
    exit 1
fi
```

`--fail` treats HTTP 400+ as failure; `--max-time` bounds request time. This is a basic availability check, not full application validation.

### Step 2 — Check syntax and run it

```bash
bash -n ~/scripts/healthcheck.sh
chmod u+x ~/scripts/healthcheck.sh
~/scripts/healthcheck.sh
```

### Step 3 — Schedule it every five minutes

```bash
crontab -e
```

Add this line **inside the crontab editor**, replacing `devops` with your account name and home path:

```cron
*/5 * * * * /home/devops/scripts/healthcheck.sh >> /home/devops/healthcheck.log 2>&1
```

The schedule means every five minutes, every hour, every day. The append log grows over time; production jobs need retention or log rotation.

### Step 4 — Verify the scheduled entry and inspect later output

```bash
crontab -l
tail -n 20 ~/healthcheck.log
```

The log may not exist until the first scheduled run. When finished, use `crontab -e` and remove only the lab's line; do not remove other jobs.

## 37. Netplan static IP example: inspect before changing

**Use case:** keep an Ubuntu VM at a known LAN address. A DHCP reservation on your router is often simpler when available.

Example assumptions:

| Setting | Example | Must verify |
| --- | --- | --- |
| Interface | `enp0s8` | Actual name from `ip -br address` |
| Ubuntu address | `192.168.1.201/24` | Correct subnet and an address reserved for this VM |
| Gateway | `192.168.1.1` | Actual router from `ip route` |
| DNS | `192.168.1.1` | Router really provides DNS, or use your network's approved resolver |

**Do not add a second default route blindly.** If your VM already has a working NAT adapter with a default route, a second adapter used for local access may need only an address, with no default route or DNS configuration. Inspect all existing Netplan files because they are merged. Cloud-init may regenerate network configuration on managed images; follow that environment's configuration method.

For a lab with **one LAN adapter** and the verified settings above:

```yaml
network:
  version: 2
  ethernets:
    enp0s8:
      dhcp4: false
      addresses:
        - 192.168.1.201/24
      routes:
        - to: default
          via: 192.168.1.1
      nameservers:
        addresses:
          - 192.168.1.1
```

Edit the appropriate existing file rather than blindly adding overlapping files. Keep your backup and VM console available. YAML needs consistent spaces, not tabs. A failed ping does **not** prove an IP is unused; confirm its availability using your router/DHCP configuration or network administrator.

Validate, then use the confirmation-based trial:

```bash
sudo netplan generate
sudo netplan try
```

Verify the IP, route, DNS, and a second SSH connection before confirming. If connectivity fails, recover through the VM console and restore the known-good configuration.

## 38. Troubleshooting: choose commands by the symptom

### A. SSH is not connecting

1. On Ubuntu: `ip -br address` — confirm the destination address.
2. On Ubuntu: `systemctl status ssh --no-pager` — check the server.
3. On Ubuntu: `sudo ss -ltnp 'sport = :22'` — confirm the listener and its bind address.
4. On Ubuntu: `sudo ufw status verbose` — inspect the firewall if UFW is used.
5. On Windows PowerShell: `Test-NetConnection 192.168.1.201 -Port 22`.
6. On the client: `ssh -v devops@192.168.1.201` — distinguish routing, connection, host-key, and authentication errors.
7. On Ubuntu: `sudo journalctl -u ssh -n 100 --no-pager` — inspect relevant logs.

| Message | Likely direction to investigate |
| --- | --- |
| Connection timed out | Wrong IP, VM adapter mode, route, or firewall dropping traffic |
| Connection refused | Reachable host rejecting the port; check SSH listener, address, and firewall rejection |
| Permission denied | Authentication or account policy; check username, key, password, and logs |
| Host key has changed | Verify server identity independently; a VM rebuild is one possible cause |

### B. Website or API is unavailable

1. `curl -v --max-time 10 http://127.0.0.1:8000/` — does it work locally?
2. `sudo ss -ltnp 'sport = :8000'` — is anything listening, and on which address?
3. `systemctl status devops-web-lab --no-pager` — is the service healthy?
4. `sudo journalctl -u devops-web-lab -n 100 --no-pager` — what failed?
5. If using Nginx: `sudo nginx -t`, then inspect its error logs.
6. If local requests work but remote ones fail, inspect binding, routing, firewall, and any cloud security group or load balancer.

An application listening on `127.0.0.1` accepts local connections only, unless you use an SSH tunnel or a proxy. `0.0.0.0` listens on all IPv4 interfaces, which changes exposure.

### C. Disk is full

1. `df -h` — which filesystem is full?
2. `df -i` — are inodes exhausted instead of capacity?
3. `sudo du -h --max-depth=1 /var | sort -h` — where is usage concentrated?
4. `journalctl --disk-usage` — are journals significant?
5. `docker system df` — is Docker storage significant, if Docker is installed?
6. `sudo lsof +L1` — are deleted files still held open?

Choose cleanup based on what you found and the retention requirements. Do not delete random files from `/var/lib`, databases, or Docker storage directories.

### D. Server is slow

1. `uptime` — compare load with CPU count; load includes tasks waiting for CPU or uninterruptible I/O.
2. `top` or `htop` — inspect active processes.
3. `free -h` — check available memory; low “free” alone can be normal because Linux caches files.
4. `vmstat 1 5` — look for sustained CPU pressure, swapping, or blocked tasks.
5. `iostat -xz 1 5` — examine disk activity if sysstat is installed.
6. `sudo journalctl -k -b --no-pager` — investigate device or memory-related messages.

### E. Permission denied when reading a file or starting a script

1. `whoami` and `id` — confirm which account and groups are active.
2. `ls -l script.sh` — inspect ownership and permissions.
3. `namei -l /full/path/to/script.sh` — inspect parent directory traversal permissions.
4. `file script.sh` and `cat -A script.sh` — inspect file format and Windows line endings.
5. `bash -n script.sh` — check Bash syntax.
6. For an intended executable script owned by you, `chmod u+x script.sh` may be the specific fix. For denied resources, establish the correct owner/group/access policy.

Do not apply `chmod 777` or run the entire application as root as a general workaround.

### F. Ubuntu has an IP but DNS names fail

1. `ip route` — check for a usable route.
2. `ping -c 4 1.1.1.1` — test IP connectivity, allowing for ICMP filtering.
3. `getent ahosts ubuntu.com` — test system name resolution.
4. `resolvectl status` — inspect resolvers if systemd-resolved is used.
5. `dig ubuntu.com` — inspect DNS behavior if dnsutils is installed.
6. Correct the active network configuration or upstream DNS issue. On managed Ubuntu systems, do not blindly overwrite `/etc/resolv.conf`.
